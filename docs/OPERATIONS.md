# Руководство оператора

Для того, кто ставит агента и отвечает за то, чтобы он работал. Дежурному —
[`DUTY.md`](DUTY.md), автору скиллов — [`KNOWLEDGE.md`](KNOWLEDGE.md).

Здесь только эксплуатация. Почему устроено именно так — в
[`docs/adr/`](adr/README.md); читать их для установки не нужно.

## 1. Что вы ставите

Один бинарь в одном контейнере, рядом файл SQLite и рабочая копия репозитория
знаний. Ни очередей, ни второго процесса, ни своей базы данных на стороне.

Агент ходит наружу в три места: источник логов, источник метрик и модель за
OpenAI-совместимым API. Ни в одно из них он не пишет. На хосты по SSH не ходит
вовсе — вместо этого оставляет дежурному заявку с командой
([ADR-0011](adr/0011-diagnostic-requests.md)).

## 2. Что нужно до установки

**VictoriaLogs и VictoriaMetrics** — читающий доступ. Логам нужен пароль, если
они за basic-аутентификацией.

**Модель за OpenAI-совместимым API.** Проверялось на llama.cpp за LiteLLM.
Требование одно и жёсткое: сервер обязан поддерживать `response_format` со
схемой JSON. Без этого агент получает от модели прозу вместо разбора и
отказывается её понимать ([ADR-0007](adr/0007-local-inference.md)).

**Репозиторий знаний** — отдельный git с каталогами `skills/`, `notes/`,
`drafts/`, `reports/`. Без него агент работает, но разбирать инциденты ему
нечем: скиллы живут там. Стартовый набор — в
[`examples/knowledge/`](../examples/knowledge/), формат — в
[`KNOWLEDGE.md`](KNOWLEDGE.md).

**Реверс-прокси с TLS.** HTTPS агент не умеет и не будет. Вход по логину и
паролю по голому HTTP означает, что пароль дежурного виден в сети целиком.

## 3. Сколько нужно ресурсов

Считайте от числа потоков, а не от объёма логов: агент хранит счётчики, а не
записи. Один поток даёт один минутный бакет в минуту.

| Что | При 200 потоках |
| :--- | :--- |
| Минутные бакеты, 7 суток | 200 × 1440 × 7 ≈ 2 млн строк, порядка 150 МБ |
| Часовые бакеты, 395 суток | 200 × 24 × 395 ≈ 1,9 млн строк, порядка 130 МБ |
| Инциденты, расследования, корпус | десятки мегабайт в месяц |
| **Диск под `/opt/data/sreagent`** | **заложите 2 ГБ** |
| Память процесса | сотни мегабайт: в памяти живут окна одного прохода |
| Процессор | считает медиану и MAD раз в минуту; доли ядра |

Это оценка по устройству хранения, а не замер: на живых данных её надо
проверить и записать сюда. Модель считает свои ресурсы сама и в этот счёт не
входит — она отдельная служба, и обычно ей нужна видеокарта.

Объём растёт от **числа потоков**, а не от гигабайт логов: сто гигабайт от
двадцати сервисов дешевле, чем гигабайт от двухсот.

## 4. Установка

Роль Ansible — [`deploy/auto-sre/`](../deploy/auto-sre/README.md). Обязательны
три переменные: `sreagent_model_key`, `sreagent_session_key` и
`sreagent_accounts`. Без них агент не стартует и говорит, какой именно
переменной не хватает.

Хеш пароля считает сам агент, чтобы пароль не уезжал на сторонний сайт:

```bash
docker run --rm sreagent:latest hash 'пароль'
```

Настройки — в [`examples/sreagent.toml`](../examples/sreagent.toml), там
описано каждое поле. Секреты в файл не кладутся никогда: только через
окружение ([ADR-0025](adr/0025-config-file-and-secrets.md)).

## 5. Как подключить модель

Настройка живёт в двух местах, и это не оплошность: адрес — в файле, ключ — в
окружении ([ADR-0025](adr/0025-config-file-and-secrets.md)).

```toml
# /etc/sreagent/sreagent.toml
[model]
url = "http://litellm:4000"                 # корень OpenAI-совместимого API
name = "gemma-4-12B-it-qat-q4_0-gguf"       # имя модели так, как его знает сервер
timeout = "180s"
max_tokens = 900
temperature = 0.2
```

```bash
# окружение контейнера
SREAGENT_MODEL_KEY=sk-…
```

В роли Ansible те же три вещи — `sreagent_model_url`, `sreagent_model_name`,
`sreagent_model_key`.

Агент дописывает к адресу `v1/chat/completions` и ходит с заголовком
`Authorization: Bearer <ключ>`. Больше он ничего не знает: любой сервер с
OpenAI-совместимым API подойдёт, менять код для этого не нужно.

**Косая черта в конце адреса значима.** Путь дописывается по правилам
разрешения ссылок, поэтому подпуть без неё теряет последний сегмент:

| В настройке | Куда пойдёт запрос |
| :--- | :--- |
| `http://litellm:4000` | `http://litellm:4000/v1/chat/completions` |
| `http://proxy/openai` | `http://proxy/v1/chat/completions` — **не то** |
| `http://proxy/openai/` | `http://proxy/openai/v1/chat/completions` |

Проверить связку до запуска агента можно тем же запросом, каким ходит он сам:

```bash
curl -s http://litellm:4000/v1/chat/completions \
  -H "Authorization: Bearer $SREAGENT_MODEL_KEY" \
  -H 'content-type: application/json' \
  -d '{"model":"gemma-4-12B-it-qat-q4_0-gguf",
       "messages":[{"role":"user","content":"верни {\"worth\": true}"}],
       "response_format":{"type":"json_schema","json_schema":{"name":"triage","strict":true,
         "schema":{"type":"object","additionalProperties":false,
                   "required":["worth"],"properties":{"worth":{"type":"boolean"}}}}}}'
```

Если сервер вернул `{"worth": true}` — связка рабочая. Если он **проигнорировал
`response_format`** и ответил прозой, агент работать не сможет: форма ответа
удерживается грамматикой на стороне сервера, а не уговорами в промпте
([ADR-0007](adr/0007-local-inference.md)).

Модель недоступна — агент не слепнет: отклонения находятся по-прежнему, отсев
при отказе пропускает их дальше, инциденты заводятся без объяснения, а в журнал
идёт «модель недоступна». Теряются только выводы.

## 6. Первый день

**Это самая частая причина решить, что агент сломан.** Сразу после установки он
молчит, и это правильное поведение.

| Когда | Что происходит |
| :--- | :--- |
| Первая минута | снимает бакеты, дозапрашивает историю на глубину базовой линии |
| Первые 6 часов | **инцидентов нет**: базовой линии пятнадцатиминутного горизонта ещё не хватает |
| Через 6 часов | горизонт 15 минут начинает судить |
| Через 25 часов | начинает судить часовой горизонт |
| Через 25 суток | начинает судить суточный |
| После полуночи | появляется первый суточный отчёт |
| Первая неделя | инциденты будут и ложные, и пропущенные: пороги не откалиброваны |

Пока базовой линии нет, в журнале на уровне `debug` идёт строка «базовой линии
ещё нет, горизонт пропущен». Это не ошибка.

Глубину дозапроса агент выбирает сам — не меньше, чем нужно самому короткому
включённому горизонту, — и пишет при старте: «дозапрос истории на старте,
minutes=375». Если в источнике истории нет, ждать придётся столько же реального
времени.

**Первую неделю смотрите на ленту глазами.** Задача этого времени — не поймать
аварию, а понять, что агент считает аварией, и подкрутить пороги.

## 7. Что открыто наружу

| Путь | Вход | Что отдаёт |
| :--- | :--- | :--- |
| `/api/health` | **без входа** | состояние и версия |
| `/metrics` | **без входа** | счётчики агента в формате Prometheus |
| всё остальное | по логину | содержимое прод-логов |
| `/api/corpus` | по логину | **прод-логи целиком**, построчным JSON |

Два первых пути открыты намеренно: их спрашивает мониторинг. Секретов в них
нет, но число инцидентов по ним видно — если это важно, закройте их на прокси
по адресу источника.

`/api/corpus` заслуживает отдельного внимания: это выгрузка живых данных для
дообучения, и она отдаёт то, что уходило в модель. По умолчанию адреса и
идентификаторы маскируются; `raw = true` отключает маскирование
([ADR-0027](adr/0027-live-corpus.md)).

Порт по умолчанию — 8096, слушает `0.0.0.0`.

## 8. Резервное копирование

Терять не жалко: ряды наблюдений — агент дозапросит их из источников сам.
Жалко: инциденты, оценки дежурного, приглушения и корпус живых данных. Оценки
дежурного невосстановимы в принципе — это работа человека.

База в режиме WAL, поэтому **копировать файл на живом агенте нельзя**: рядом
лежат `sre.db-wal` и `sre.db-shm`, и копия без них битая. Два верных способа:

```bash
# Способ первый: снять копию на живой базе средствами SQLite
sqlite3 /opt/data/sreagent/sre.db ".backup '/var/backups/sre-$(date +%F).db'"

# Способ второй: остановить агента и скопировать все три файла
docker compose stop agent
cp /opt/data/sreagent/sre.db* /var/backups/
docker compose start agent
```

Первый предпочтительнее: агент продолжает работать. `sqlite3` в образ агента не
входит — ставьте на хост.

Восстановление — положить файл на место и поднять агента. Схема при подъёме
приводится в порядок сама: шаги применяются по предложению, и уже сделанное
пропускается, поэтому база из старого бэкапа не роняет новую версию
([ADR-0023](adr/0023-deploy-with-downtime.md)).

Репозиторий знаний бэкапится как обычный git — он и есть бэкап самого себя,
если его пушат.

## 9. Обновление и откат

Обновление — остановка, подмена образа, старт. Окно слепоты равно времени
перезапуска, пропущенные минуты агент дозапросит.

Откат — возврат прежнего образа на ту же базу. Работает, потому что каждый
запрос называет свои столбцы поимённо: столбцы, добавленные новой версией,
прежней не мешают.

**Выкладка в разгар аварии стоит находок.** Прерванные расследования при
подъёме закрываются, а инциденты разбираются заново с чистого листа. Если
можно подождать — подождите.

## 10. За чем следить

Полный список показателей — [`METRICS.md`](METRICS.md). Минимум, ради которого
стоит завести алерты:

**`time() - sre_last_bucket_timestamp_seconds > 300`** — агент ослеп. Главный
алерт: процесс жив, отвечает на проверку здоровья, и не видит ничего.

**`rate(sre_source_failures_total[15m]) > 0`** — источник или модель отвечают
отказом.

**`sre_skipped_total` растёт** — очередь не успевает, инциденты доходят до
дежурного без разбора. Либо модель медленная, либо шума слишком много.

## 11. Что делать, когда

**Агент не находит ничего, а логи есть.** Смотрите `sre_deviations_total`. Ноль
на молодой установке — нормально, см. §6. Ноль на старой — проверьте страницу
`/series`: там видно, за чем агент наблюдает на самом деле. Пустая страница
означает, что до источника он не доходит.

**В журнале «промежуток не снят и остался дырой».** Источник не ответил.
Единичные строки безобидны — дыра закроется дозапросом. Постоянные означают,
что источник недоступен или запрос слишком тяжёл: уменьшите `chunk`.

**«источник вернул минуты вне запрошенного промежутка: разошлись часы».** Время
на хосте агента и на источнике разъехалось. Проверьте NTP: при расхождении
больше минуты бакеты будут отбрасываться, и ряд перестанет сходиться.

**«подходящего скилла нет: разбирать нечем».** Инцидент завёлся на горизонте, для
которого нет ни одного скилла. Проверьте, что репозиторий знаний примонтирован
и `digging.skills` указывает в его `skills/`. Строка «скиллы загружены,
skills=N» при старте покажет, сколько прочиталось.

**«сигнал скилла неизвестен агенту: скилл не применится ни разу».** Опечатка во
фронтматтере скилла. Допустимые значения — `errors`, `metric`, `any`.

**«вывод пропущен: очередь не дошла за отпущенное время».** Инцидент простоял в
очереди дольше `digging.patience` и дошёл до дежурного голыми числами.
Увеличьте `digging.parallel`, если модель тянет, или примите как есть: молчать
в этом случае хуже.

**«модель недоступна».** Разбор не состоится, но инциденты заводиться не
перестанут: отсев при отказе модели пропускает отклонение дальше. Агент не
слепнет от того, что молчит модель.

**Инцидентов сотни в первый день.** Пороги не откалиброваны. Не выключайте
агента — приглушите самые шумные пары (это записывается с автором и сроком) и
поднимите `minimum` и `score` для горизонта. Приглушение с истечением лучше
глухого порога: оно само напомнит о себе
([ADR-0019](adr/0019-muting-instead-of-per-service-thresholds.md)).

**База заблокирована.** Один агент на одну базу. Двух процессов на одном файле
быть не должно; при подозрении проверьте, не остался ли прежний контейнер.

## 12. Чего агент не делает

Не чинит, не перезапускает, не ходит на хосты, не пишет в источники, не шлёт
уведомления. Узнать о новом можно только глядя в веб-морду или по своим
алертам на метрики агента.

Это не список недоделок, а граница: она выбрана осознанно и записана в
[`SPEC.md`](SPEC.md).
