# Спецификация: агент диагностики

Статус: черновик. Ведётся до кода и правится раньше кода — если поведение
разошлось со спекой, неправ код.

Версия 0.1 · заведена 14.08.2026

---

## 1. Задача

Второй контур наблюдения за прод-системой. Агент постоянно смотрит логи и
метрики, замечает отклонения, **сам проводит первичную диагностику** и
показывает дежурному разбор: что случилось, где, на что похоже из уже
известного, куда смотреть дальше.

Агент **не чинит**. Починка — работа SRE. Агент сокращает время до обнаружения
и время до понимания.

### 1.1 Масштаб и первая система

Пилот идёт на логах самого AI-проекта: стенд инференса, LiteLLM, сам агент.
Нагрузка там небольшая, зато данные свои — можно ошибаться, не мешая чужому
дежурству.

Целевой масштаб, под который проектируем: **около 200 сервисов, 50 ГБ логов в
сутки** в VictoriaLogs. Отсюда два требования: счётчики снимаются агрегатами на
стороне источника, а не выгрузкой строк; число запросов за проход не зависит от
числа сервисов.

Отдельное следствие пилота: агент смотрит на логи, в которые сам же пишет.
Исключение собственных потоков — не мелочь эксплуатации, а условие работы:
без него агент находит себя, разбирает себя и пишет о себе.

### Чего агент не делает на первом этапе

- не выполняет команды на прод-хостах и не ходит по SSH;
- не меняет конфигурации, не перезапускает сервисы, не крутит ручки;
- не заменяет алертинг: у существующего мониторинга своя роль, агент рядом,
  а не вместо.

## 2. Действующие лица

| Лицо | Что делает | Что получает |
| :--- | :--- | :--- |
| **Дежурный SRE / DevOps** | читает вывод, выполняет заявки на диагностику, оценивает инциденты, дописывает причину | канал диагностики и подсказку, куда смотреть |
| **Автор скиллов** (тот же SRE) | пишет скиллы анализа и заметки базы знаний | способ передать агенту свой опыт без программиста |
| **Руководитель** | читает недельный отчёт | картина здоровья системы на понятном языке |
| **Агент** | наблюдает, подозревает, расследует, пишет отчёты и черновики знаний | — |

## 3. Глоссарий

Термины обязательны к употреблению в коде, интерфейсе и разговоре. Одно
понятие — одно слово.

| Термин | Значение |
| :--- | :--- |
| **Бакет** (bucket) | Числовой факт за одну минуту: счётчик событий потока или значение метрики. Берётся из источника, не интерпретируется |
| **Ряд** (series) | Бакеты одного потока подряд. Накапливается у нас и переживает сырые логи |
| **Поток** (stream) | Селектор источника логов — то, что источник считает отдельной струёй записей |
| **Сервис** (service) | Имя, вытащенное из потока. Половина ключа инцидента |
| **Сигнатура** (signature) | Сообщение об ошибке с замаскированными числами, адресами и идентификаторами. Вторая половина ключа инцидента |
| **Отклонение** (deviation) | Ряд, вышедший за пороги детектора на одном горизонте. Решение числовое и воспроизводимое |
| **Подозрение** (suspicion) | Отклонение, которое дешёвый отсев моделью счёл достойным разбора. Решение модельное и недетерминированное |
| **Расследование** (investigation) | Ограниченный по шагам сбор данных вокруг подозрения плюс работа модели над ними |
| **Досье** (dossier) | Данные, собранные шагами расследования и уходящие в модель |
| **Вывод** (conclusion) | Итог расследования: версия причины, уверенность, рекомендация куда смотреть |
| **Важность** (severity) | Насколько всё плохо. Категория, её ставит модель — в отличие от веса, который считает агент |
| **Оценка** (verdict) | Суждение дежурного об инциденте: по делу или ложный. Единственный источник метрики точности |
| **Инцидент** (incident) | Долгоживущая сущность: сгруппированные подозрения об одной беде, все расследования по ним, заявки и отчёты. Единственное, к чему применимо «время до обнаружения» |
| **Вес** (weight) | Число, по которому упорядочена очередь расследований: сила отклонения, охват, известность сигнатуры, важность сервиса |
| **Связь** (relation) | Пометка, что два инцидента начались в одном окне. Подсказка человеку, а не группировка |
| **Приглушение** (mute) | Временное молчание по паре «сервис плюс сигнатура»: срок, автор, причина |
| **Заявка** (inquiry) | Просьба агента к человеку снять диагностику, которую агент снять не может. Возвращается выводом в карточку |
| **Скилл** (skill) | Markdown-файл: когда применять, какие запросы снять, на что смотреть. Пишет человек, читает агент |
| **Заметка** (note) | Единица базы знаний: известная ошибка, разобранная авария, приём диагностики. Markdown в git |
| **Черновик** (draft) | Заметка, написанная агентом и ждущая приёмки дежурным |
| **Горизонт** (horizon) | Уровень анализа: ширина окна, период оценки, пороги и набор скиллов. Задаётся настройкой; по умолчанию включены 15 минут, час, сутки |
| **Коннектор** (connector) | Наш код, ходящий в источник |
| **Источник** (source) | Внешняя система с данными: VictoriaLogs, VictoriaMetrics, дальше — прочие |
| **Отчёт** (report) | Документ для человека: по инциденту, по горизонту, недельный для руководителя |

Слова **«аномалия»**, **«наблюдение»** и **«разбор»** годятся для отчётов и
разговора, но отдельных сущностей за ними нет: в коде, в базе и в интерфейсе
живут только термины из таблицы. Слово **«находка»** запрещено совсем — оно
означало то подозрение, то инцидент.

Отображение терминов в имена типов, таблиц и полей — [`NAMES.md`](NAMES.md).

## 4. Конвейер

```
коннекторы → наблюдения → [детектор] → отклонения → [отсев моделью] → подозрения
                                                                          ↓
                            инцидент ← группировка ←  [расследование] ←──┘
                               ↓                            ↑ ↓
                            отчёты                  база знаний, заявки
```

Три решателя стоят по возрастанию цены: детектор считает числа и стоит
доли секунды, отсев спрашивает модель одним коротким промптом, расследование
тратит минуты инференса. Дорогое включается только там, где дешёвое уже
сказало «смотри сюда» — см. [ADR-0001](adr/0001-two-contours.md).

### 4.1 Наблюдение и детектор

Детектор работает на числах и ничего не знает про модель. Требования:
робастность к собственным выбросам, объяснимость решения («счётчик 91 против
медианы 4.5»), настраиваемые пороги на горизонт.

Правил два, потому что сигналы разные. У логов считается **число событий** —
всплеск виден как рост счётчика. У метрик важны **уровень и направление**:
память, которая растёт третий час, не даёт всплеска ни в одном окне.

Наблюдаемые серии метрик отбираются правилами, универсальный набор идёт в
поставке — [ADR-0016](adr/0016-observed-metrics.md).

### 4.2 Отсев

Один короткий промпт: «вот отклонение и его числа, стоит ли разбираться?».
Отсекает регулярный шум, который порогами не описать (ночная выгрузка,
известный болтливый сервис). Ответ по схеме: да/нет и одна фраза почему.

### 4.3 Очередь

Расследований одновременно идёт не больше, чем тянет стенд. Очередь
упорядочена по **весу** отклонения. Подозрение, простоявшее дольше срока,
заводит инцидент без разбора — голыми числами, с пометкой «разбор пропущен»
([ADR-0018](adr/0018-investigation-queue.md)).

Отсюда правило, которое важнее прочих: **инцидент доходит до дежурного, даже
если модель недоступна**. Без вывода, но доходит.

### 4.4 Расследование

Ведёт скилл: он задаёт первое досье. Дальше модель может запросить добор
данных из фиксированного меню, не более K шагов — [ADR-0002](adr/0002-bounded-tools.md).
В расследование входит поиск похожего в базе знаний.

Итог расследования: версия причины, уверенность, рекомендация «куда смотреть»,
при нехватке данных — заявка человеку.

### 4.5 Инцидент

Ключ инцидента узкий: сервис плюс сигнатура для логов, сервис плюс метрика для
метрик. Инциденты, начавшиеся в одном окне, помечаются **связанными** —
объединяет их человек, а не агент ([ADR-0017](adr/0017-narrow-grouping.md)).

Инцидент живёт, пока приходят подтверждения, и закрывается тишиной или
человеком. К нему крепятся расследования, заявки, оценки дежурного и итоговый
отчёт — [ADR-0010](adr/0010-incident-aggregate.md).

### 4.6 Шум

Основной глушитель — отсев: «этот сервис ругается каждую ночь» описывается
фразой, а не порогом. Сверху ручное **приглушение** пары «сервис плюс
сигнатура» на срок ([ADR-0019](adr/0019-muting-instead-of-per-service-thresholds.md)).

Приглушение всегда истекает, а приглушённое продолжает копиться тихо и попадает
в суточный отчёт строкой «приглушено, но продолжается».

## 5. Горизонты

У каждого горизонта свой вопрос, свой набор скиллов и свой отчёт —
[ADR-0006](adr/0006-four-horizons.md). Набор горизонтов задаётся настройкой, а
не зашит в код — [ADR-0014](adr/0014-horizons-are-configurable.md).

Считаются они не отдельными запросами, а поверх одного накопленного ряда:
агент раз в минуту снимает минутный бакет, горизонт — сумма последних N бакетов
([ADR-0013](adr/0013-minute-buckets.md)). Суточный горизонт работает по часовым
бакетам.

| Горизонт | Ширина | Период оценки | Вопрос | По умолчанию |
| :--- | :--- | :--- | :--- | :---: |
| **15 минут** | 15 мин | 1 мин | что горит и развивается ли | вкл |
| **час** | 60 мин | 5 мин | что тихо деградирует: утечки, диски, латентность, ретраи | вкл |
| **сутки** | 24 ч | 1 ч | что повторяется: темы дня, возвращающиеся инциденты | вкл |
| **5 минут** | 5 мин | 1 мин | короткие резкие всплески | выкл |

**Ширина окна и задержка обнаружения — разные вещи.** Задержку задаёт период
оценки: пятнадцатиминутное окно, пересчитываемое каждую минуту, замечает
отклонение за те же две минуты, что и пятиминутное. Короткий горизонт нужен для
чувствительности к всплескам длиной в минуты, а не для скорости.

Пятиминутный горизонт выключен по умолчанию сознательно: на малых объёмах в
пятиминутном окне слишком мало событий, базовая линия считается по шуму, и
любое отклонение выглядит бесконечным.

## 6. Скиллы

Markdown с фронтматтером — [ADR-0003](adr/0003-skills-as-markdown.md).
Запросы пишутся на родном языке источника с пометкой коннектора —
[ADR-0005](adr/0005-native-queries.md). Форма описана в
[`docs/KNOWLEDGE.md`](KNOWLEDGE.md), рабочие образцы — в
[`examples/knowledge/skills/`](../examples/knowledge/skills/).

Вид скилла:

```markdown
---
name: errors-versus-load
title: Ошибки против нагрузки
horizon: 15m
when:
  signal: errors
collect:
  - id: signatures
    vl: '_time:[{start}, {end}) {stream} (i(error*) OR i(timeout*)) | fields _msg'
    limit: 100
  - id: rps
    vm: 'sum(rate(http_requests_total{job="{service}"}[{horizon}]))'
tools: [logs, metrics, knowledge]
---

Сопоставь рост ошибок с нагрузкой на сервис.

Ошибки выросли, запросы не выросли — проблема внутри сервиса или в том, от чего
он зависит. Выросло и то и другое — сервис захлебнулся нагрузкой, ищи источник
запросов выше по цепочке.
```

## 7. База знаний

Markdown в **отдельном репозитории** — [ADR-0015](adr/0015-knowledge-repository.md).
Там же живут скиллы и отчёты: всё, что пишут и читают люди, лежит в одном месте,
и SRE не нужен доступ к коду.

Устройство репозитория и форматы файлов — [`docs/KNOWLEDGE.md`](KNOWLEDGE.md).
Рабочий образец, он же стартовый набор — [`examples/knowledge/`](../examples/knowledge/).

Черновик принимается кнопкой в карточке инцидента: агент переносит файл из
`drafts/` в `notes/` коммитом. Уход в git ради заметки — верный способ не
сделать этого никогда.

Поиск полнотекстовый по телу, тегам и сигнатурам —
[ADR-0008](adr/0008-full-text-knowledge-search.md). Агент пишет только
черновики, в базу их переводит дежурный —
[ADR-0009](adr/0009-drafts-before-knowledge.md).

Виды заметок: известная ошибка (сигнатура → смысл → что делать), разбор
аварии (что было, причина, как чинили), приём диагностики (как смотреть).

## 8. Коннекторы

Общий трейт, набор собирается фичами под конкретную систему —
[ADR-0004](adr/0004-connectors-as-features.md). На первом этапе:
VictoriaLogs и VictoriaMetrics. Дальше — Zabbix, Jira и прочее.

Коннектор отвечает за: перечисление сущностей (потоки, серии), снятие ряда
по окнам, выборку сырых записей, выполнение произвольного родного запроса.

## 9. Отчёты

| Отчёт | Когда | Для кого |
| :--- | :--- | :--- |
| По инциденту | при закрытии инцидента | дежурный, разбор полётов |
| По горизонту | по расписанию горизонта, если есть о чём | дежурный |
| Недельный | раз в неделю | руководитель |

**Суточный отчёт** — четыре части:

1. **Инциденты** — что заводилось, чем кончилось, что осталось открытым.
2. **Аномалии** — отклонения и подозрения, не ставшие инцидентами, включая
   приглушённые: «приглушено, но продолжается».
3. **Динамика** — что растёт: число аномалий по сервисам против вчерашнего, и
   параметры, идущие не туда. Здесь же попытка оценить, когда показатель
   упрётся в предел, если так пойдёт дальше.
4. **Общая картина** — верхнеуровневый взгляд: где система здорова, где нет,
   на что смотреть завтра.

**Недельный отчёт** — четыре части: доступность за неделю, главные проблемы по
числу и весу, сравнение с прошлой неделей, что по этим проблемам делали люди.
Без последней части отчёт превращается в список жалоб.

Часть «динамика» — единственное место, где агент смотрит дальше своего
горизонта. Она собирается по накопленным рядам, а не запросами к источнику
([ADR-0013](adr/0013-minute-buckets.md)), и по свёрнутым часовым бакетам
достаёт до прошлого года ([ADR-0022](adr/0022-retention.md)).

Отчёт — markdown-файл в репозитории знаний (`reports/`) плюс страница на вебе. Отправка в мессенджеры —
следующий этап, формат к ней уже готов.

## 10. Веб-морда и доступ

Вход по логину и паролю, учёток несколько, ролей нет —
[ADR-0020](adr/0020-login-and-password.md). Общая учётка на смену не годится:
приглушения и приёмки черновиков подписываются именем, и подпись «дежурный»
обесценит и то, и другое.

Что дежурный делает в интерфейсе:

| Действие | Зачем |
| :--- | :--- |
| видит раздел «ждёт вас» со счётчиком | заявки, вопросы по прерванным расследованиям и черновики в одном месте |
| читает ленту инцидентов и карточку | основная работа |
| оценивает инцидент: по делу или ложный | единственный источник метрики точности |
| объединяет и разделяет инциденты | исправляет ошибки группировки ([ADR-0017](adr/0017-narrow-grouping.md)) |
| отвечает на заявку диагностики | замыкает петлю расследования ([ADR-0011](adr/0011-diagnostic-requests.md)) |
| принимает или правит черновик знания | пополняет базу ([ADR-0009](adr/0009-drafts-before-knowledge.md)) |
| приглушает пару «сервис плюс сигнатура» | гасит шум ([ADR-0019](adr/0019-muting-instead-of-per-service-thresholds.md)) |
| закрывает инцидент | завершает работу и запускает отчёт |

Раздел «ждёт вас» — единственный способ узнать о заявке, пока нет мессенджеров.
Поэтому просроченное из него попадает в суточный отчёт: заявка, о которой никто
не узнал, останавливает расследование и держит инцидент открытым.

HTTPS делается на входе реверс-прокси и в задачу агента не входит. Пароль по
голому HTTP — дыра, и в инструкции по развёртыванию это написано прямым текстом.

## 11. Устойчивость

**Чего нет на диске — того не было** ([ADR-0021](adr/0021-state-survives-restart.md)).
Очередь, шаги расследований, инциденты, заявки и приглушения пишутся до того,
как понадобятся. Полусостояний в памяти не остаётся.

При старте агент поднимает очередь и незакрытые инциденты, дозапрашивает дыры в
рядах наблюдений и разбирается с прерванными расследованиями: понятно, как
продолжить — продолжает; непонятно — спрашивает дежурного; дежурный не знает —
инцидент закрывается пометкой «оставлено без разбора».

Сроки хранения — [ADR-0022](adr/0022-retention.md): минутные бакеты семь суток,
часовые тринадцать месяцев, расследования девяносто дней, инциденты год, отчёты
бессрочно.

**Выкладка** — Ansible и один контейнер на одном хосте, обновление с остановкой
([ADR-0023](adr/0023-deploy-with-downtime.md)). Окно слепоты равно перезапуску,
ряд восстанавливается дозапросом. Откат — прежний образ, поэтому миграция схемы
одного шага оставляет базу пригодной для предыдущей версии.

**Наблюдение за самим агентом** — он публикует свои метрики, их собирает
VictoriaMetrics, алерты живут в существующем мониторинге
([ADR-0024](adr/0024-agent-under-watch.md)). Главный показатель — свежесть
последнего снятого бакета: процесс может быть жив и слеп, и это то же самое,
что лежать.

**Настройки** — файл TOML под Ansible; секреты только из окружения
([ADR-0025](adr/0025-config-file-and-secrets.md)).

## 12. Приёмка

Считаем на живых данных, не на синтетике.

| Критерий | Цель | Как меряем |
| :--- | :--- | :--- |
| Время до обнаружения | **5 минут**, 90-й процентиль | от появления отклонения в данных до заведения инцидента |
| Время до вывода | **15 минут**, 90-й процентиль | от появления отклонения до готового вывода расследования на карточке |
| Доля ложных инцидентов | не выше 30% на второй месяц | оценки дежурного в карточке |
| Полнота | ни один инцидент, замеченный людьми, не пропущен агентом | сверка с журналом дежурств, относительно включённых горизонтов |
| Недельный отчёт | выходит без ручной правки | факт |
| Нагрузка на стенд | снятие минутного бакета укладывается в 10 секунд | замер |
| Настройка | три горизонта из коробки работают без подкрутки порогов на сервис | факт |
| Доля без вывода | не выше 10% подозрений доходит до дежурного без расследования | счётчик агента |

### 12.1 Откуда взялись две цифры

Обнаружение и вывод упираются в разное, поэтому меряются порознь.

**Пять минут до обнаружения.** Бюджет: запаздывание индексации в источнике,
плюс период съёма, плюс сам проход, плюс заведение инцидента. Схема «дождались
конца пятиминутки» этот бюджет не проходит по построению — отклонение,
начавшееся сразу после прохода, ждало бы десять минут. Поэтому наблюдения
снимаются минутными бакетами, а горизонт считается поверх накопленного ряда:
[ADR-0013](adr/0013-minute-buckets.md). Реальная задержка выходит около двух
минут, три минуты остаются запасом на запаздывание индексации. Ширина самого
короткого включённого горизонта на это время не влияет — влияет период оценки
([ADR-0014](adr/0014-horizons-are-configurable.md)).

**Пятнадцать минут до вывода.** Здесь узкое место — инференс: около 24 токенов
в секунду на декоде, отсев плюс расследование с добором данных дают несколько
минут даже при мгновенном обнаружении. Это та цифра, которую чувствует
дежурный, и та, за которую придётся бороться промптами и объёмом досье.

Если выбирать, что важнее, — вторая. Обнаружение без вывода даёт дежурному
только повод посмотреть самому.
